## 1. Prime directives (non-negotiable)

1. **TaskTracker is the only task system.** No TodoWrite, no `docs/plans/*.md`, no private checklists. Every piece of work happens under a TaskTracker task: `tasktracker_setActiveTask` on the phase and then on each sub-task as you work it, status updates as they happen, and when a phase ends the active task moves back to the cost ledger. Never `clearActiveTask`: usage with no active task is unattributed. Design notes go to sub-tasks (phase bodies are locked). Defects, learnings and frictions go to TaskTracker insights.
2. **TaskTracker is the cost ledger.** Token usage and API-equivalent cost are recorded per task, per phase, per release and for the project, every iteration (§6).
3. **Zero-error policy.** A phase is not passed while any defect or error exists — in the phase or anywhere else in the project. Every failure is fixed now, not later. No deferrals, no "known issues", no skipped/disabled tests, no `wontfix` on real bugs, no weakened assertions to make something pass (§5).
4. **Honesty over progress.** Never mark an acceptance criterion satisfied without evidence you produced this session. Never claim a check ran that didn't. Never simulate a human verification. If something can't be verified by you, it goes to the human queue (§7) and its criterion stays unsatisfied.
5. **No self-declared descoping.** You may add work (sub-tasks, phases, requirements discovered during implementation). You may not remove, weaken or silently skip a requirement, acceptance criterion or phase. If something is truly impossible, leave it open with the reason recorded and move on to other ready work.
6. **Plan first, then implement — and keep the plan true.** If the project (or a new increment) isn't planned, plan it before implementing (§3). When implementation reveals something the plan missed, update TaskTracker before or alongside the code.
7. **Verification-first.** Tests (from the acceptance criteria, with a distractor that fails a plausible wrong implementation) are written and seen failing before the implementation. Verify in the real system ({{REAL_SYSTEM}}) before calling anything done.
<!-- if:deployed -->
8. **Production stays healthy.** If a deploy of yours degrades anything on {{PRODUCTION_HOST}}, fix forward or revert immediately — that is the top priority of the iteration.
<!-- end:deployed -->

## 3. Planning mode (the plan is dynamic)

Use the TaskTracker-native skills, deciding autonomously instead of asking ({{OWNER}} is offline):
- **Brainstorm** (`/{{SKILL_PREFIX}}tt-brainstorm`): only if the brainstorm lifecycle row isn't satisfied, or a genuinely new capability appears. Record every choice with `tasktracker_recordBrainstormDecision`, marking your own choices `metadata.source: "claude"` and giving the rationale.
- **Requirements**: one requirement per user story / rule / technical need, with Given/When/Then acceptance criteria taken from the docs (verbatim in substance). Requirements you derive yourself (no source story) are created as `draft` and a human-queue item asks {{OWNER}} to approve them; you may implement them meanwhile.
- **Whole product**: plan every prioritised release (Must, then Should and Could as later releases), not only the first one a document defines. Release scope decides order and gates, not plan coverage.
- **Architecture**: register components/relationships the work will touch; keep `codeReferences` current so the drift check passes.
- **Phases** (`/{{SKILL_PREFIX}}tt-create-plan`, `tasktracker_createPhaseFromTemplate`): one concern per phase, tests before implementation, requirement links on the phase, dependencies via `tasktracker_createTaskDependency`, a verification approach + Build/Runtime/Functional exit conditions + ADR reference in the phase description, and no TBDs. Tag titles with the release (`[R2]` …).
- **Changing the plan during implementation**: add sub-tasks to the current phase or create follow-up phases (linked, with dependencies). Never edit a locked phase body — use its "Design + decision note" sub-task. Significant design choices get an ADR, where §0's Decisions row says ADRs live.
- **Deciding without {{OWNER}}**: apply the precedence (§0), then the precedent of the pattern sources (§0), then the simplest option that satisfies every acceptance criterion. Record the decision (brainstorm decision or ADR) and add a human-queue item only if {{OWNER}} should review it later. Do not block on it.

## 4. Implementation mode

### 4.1 Executing a phase
- Run the phase with `/{{SKILL_PREFIX}}tt-implement-phase <phase-id>` semantics: `setActiveTask` on the phase and each sub-task, sub-task statuses as you go, test sub-task before implementation sub-task, defects/learnings as insights.
- **Implementation agents run on the orchestrator's model.** Implementation always goes to `{{IMPLEMENTER_AGENT}}` with no `model`, so it inherits yours — never to an agent type that pins a model of its own. Put the TDD contract in the prompt: RED→GREEN evidence, a distractor for each acceptance criterion, and no git. Why: an implementer type pinned to an older model cost 25 % more per input/output token and 2.5× more per cache read, and cache reads are most of the tokens; one phase cost $194 on it.
  - For every other role (review, UI verification), check which model the agent type's definition pins (`model:` in its frontmatter) and what it costs before using it, and prefer the cheaper of two that do the job.
- Delegate code work to subagents: implementation as above; {{REVIEW_AGENT}} for review;<!-- if:browser-e2e --> `browser-verification-agent` or Playwright for UI checks;<!-- end:browser-e2e --> and the `security-review` skill for auth, user input, DB and secrets.
- Give each subagent the phase id, the exact acceptance criteria, the file boundaries, and "no git operations — the orchestrator commits".
- **Every brief carries the rules that only bite later** (<!-- if:ci -->in CI, or <!-- end:ci -->when the machine is busier): the time budget (§4.4), the hygiene list (§5.1) and the evidence you want back, with measured durations. Before <!-- if:remote -->pushing<!-- end:remote --><!-- if:!remote -->committing<!-- end:!remote -->, confirm the report shows those numbers. Why: a rule that lived in this file but not in the brief let a phase pass locally and fail CI.
- Before dispatching a subagent, make sure the active task is the sub-task it works on<!-- if:token-tooling -->, and map named subagents in the task map (token attribution, §6)<!-- end:token-tooling -->.
- **Heartbeats make agent work visible, and billable, in TaskTracker.** TaskTracker credits a token message to a task only when it falls inside a time-log segment of this session's lease. A segment stays open only while heartbeats arrive, and a gap over 5 minutes closes it. Heartbeats come from TaskTracker MCP tool calls through this session's MCP server, and teammates share it. Why: without them, the segments of one long phase covered 85 of 366 minutes, so TaskTracker showed 27 % of the real cost.
  - Set the phase active before spawning its implementer, and do not switch the active task while the implementer runs.
  - Tell every implementation and review agent to call `tasktracker_getCurrentTimer {taskId: <phase>}` after each step, after any command longer than about 4 minutes, and at least every 4 minutes. Tell it never to call `setActiveTask`.
    - The heartbeat runs only while the agent works. An agent waiting for a reply must not poll, because every poll is a paid turn.
    - A foreground command can't heartbeat while it runs. Tell agents to cut long waits into chunks of 4 minutes or less, and heartbeat between them. For example: start the gate in the background, then repeat `timeout 230 bash -c 'while kill -0 $PID; do sleep 20; done'` → `getCurrentTimer` until it ends.
    - Review agents without MCP tools (`feature-dev:code-reviewer`, for one) cannot heartbeat. TaskTracker books their cost as project overhead, while the ledger credits it correctly.
  - **Never call `tasktracker_startTimer`; call `stopTimer` only to stop a timer found running at a phase close (§5.1 checklist).** Started timers create lease-less rows that match any session's messages, so other projects' cost lands on your phase, and `stopTimer` stamps an orphaned row with the current time, which invents hours of work. Why: one phase's log read 12 h 18 m against 3 h 16 m of real time.
  - Two phases run in parallel in one session cannot both be timed. For those, only the local task-mapped report (§6) is right; say so in the ledger.
<!-- if:token-tooling -->
  - The token push runs its TaskTracker MCP child under a session id of its own, so it never takes the session's lease. TaskTracker's own global Stop hook still does, so expect short segments at turn ends.
<!-- end:token-tooling -->
  - Per-phase figures in TaskTracker stay approximate while attribution is by time segment. The ledger's local figures are the authority.
- **Agents miss background-task notifications, and idle messages can drop.** An agent that starts a command in the background and idles "until the watcher fires" never wakes up. Why: one agent went silent for 90 minutes that way.
  - Tell every agent to run long commands in the foreground, or to poll a background job's pid and log with a foreground loop kept under the tool's 10-minute limit. Tell it never to end a turn waiting on a notification.
  - Tell every agent to write its final report to a file you name in the brief before it messages you, and read that file rather than waiting on the message.
  - If an agent's files and log stop changing for 20 minutes with nothing running, nudge it once. If it still doesn't respond, stop it and hand the rest to a fresh agent with the context written into the prompt.
- **Waiting for a process:** never inline `pgrep -f <pattern>` in a shell command that also contains the pattern. The command's own `bash -c` matches it, so the wait never ends, and it blocks every other waiter too. Put the wait in a script file and call it by path, as `scripts/run-orch-gate.sh` does. After starting any long background job, confirm within a minute that its log has begun before scheduling a long wakeup. Why: a self-matching wait held a gate back for 40 minutes before anyone noticed.
- **Infrastructure that writes into the working tree** (compose stacks, generators, hooks): verify its side effects on the host, not just its happy path — file ownership, a host build afterwards, a crashed container detected fast. Give every wait in a check a timeout, and check that the check fails for the right reason.
- Keep the main context lean: verify through on-disk artifacts and command output, not by reading subagent transcripts.

## 5. The zero-error phase gate

### 5.1 A phase may be marked `completed` only when all of these hold — checked in this iteration, with the command output summarised as evidence on the phase's verify sub-task
Walk the list item by item at every close, including the items that are not tests. A working tree holding other agents' in-flight files proves nothing about the commit. The runner takes a lock so runners go one at a time, waits for any other gate, reinstalls when a lockfile changed, and ends its log with `gate exit=<code>`; read that line, not the shared `<worktree>.done` marker, for this run's result. Exit 2 means it refused its configuration, exit 3 that it waited too long.

The gate's commands: `{{GATE_COMMAND}}`, which runs:
{{GATE_CHECKS}}

Why: costs recorded only in completion caveats left one ledger two days stale, showing $1 248 against $2 129 real.

**Phase-close checklist.** Check each item at every close; these drift silently when skipped:

- **Sub-tasks:** every sub-task of the phase is completed or moved to the human queue. Also check older phases for stragglers: work done in code but never marked done.
- **Active task:** set to the current work, or to the cost ledger between phases.

## 6. Token and cost tracking in TaskTracker

<!-- if:token-tooling -->
### 6.1 The tooling
Installed in this repo: `scripts/token-usage.mjs` (the CLI; `--help`), `tooling/token-usage/` (source and tests), `scripts/pricing.json`, the Stop/SubagentStop/SessionEnd hooks in `.claude/settings.json`, and `.claude/usage/tasktracker.json` (the project id). Where TaskTracker's MCP server is, is machine-specific: `TASKTRACKER_MCP_DIR`, or `.claude/usage/tasktracker.local.json` (gitignored). It reads every main and subagent transcript, deduplicates each API response (logged once per content block; summing raw lines overcounts about 7.5×), attributes it to the task made active by `setActiveTask` at that moment, and appends it to `.claude/usage/token-usage.jsonl`. Its tests are the contract: `node --test tooling/token-usage/test/*.test.mjs`.
- **Pricing** is `scripts/pricing.json`, in USD per million tokens. An unknown model gets `costUsd: null` plus a `learning` insight asking for its price. Never guess a price; add a model from TaskTracker's rate card or the `claude-api` skill's model table. Rates marked `"verified": false` (fast mode's cache rates, for one) are assumptions: say so in the ledger.
- Cost is the **API-equivalent list price**. Say so in the ledger, because a subscription plan is billed differently.
- `--backfill` rescans every transcript of this project; `--json` gives machine-readable output.

### 6.2 Every iteration (steps B and E)
