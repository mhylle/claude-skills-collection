# `DESIGN_LANGUAGE.md` — the contract format

This is the authoring spec for **`DESIGN_LANGUAGE.md`**, the contract the
`design-language` skill writes into every `./design-system/` it produces
(generated by `scripts/assemble_dashboard.py`; spec §12). This file is the
human/maintainer specification of that structure — what each section means, why
it's there, and what a rendered contract looks like.

**`DESIGN_LANGUAGE.md` is THE artifact** that makes a *future* Claude session
build in *this* language rather than reaching for its own defaults. It is the
durable output the whole skill exists to produce. A session that is about to
generate any UI in a project governed by this design system **must read
`DESIGN_LANGUAGE.md` first** — it is the law for that project's look. The
interactive dashboard is for humans; this file is for the next agent.

Where this file and `docs/design-language-skill-spec.md` disagree, the
`scratchpad/BUILD_CONTRACT.md` schemas win.

## The six sections

The contract is six sections, **in this fixed order**. The order is intentional:
identity and the anti-reference come first because they frame every decision
below them.

### 1. Identity

The **north-star adjectives** (from Phase 0 `adjective-pick`) and a single
one-paragraph statement of *what this language is*. This is the "if you read
nothing else" summary — it sets the emotional and aesthetic target so a future
session has a center of gravity before it reaches the rules.

### 2. Anti-reference

> "This language must **NEVER** look like: [the default Claude/Anthropic
> aesthetic + the user's hard constraints]."

The union of two sources: the generic default-Claude look (see
`references/anthropic-anti-reference.md`) **and** the user's specific hard
constraints recorded in Phase 0 (`brief.json` →
`northStar.antiReferences` + `northStar.hardConstraints`).

This section is **non-negotiable, and it comes second on purpose.** Escaping the
default is the entire reason the skill exists (spec §1, §13) — a language that
quietly drifts back to warm-beige-and-clay is a *failed* language no matter how
nice it looks. Putting the "never" right after the identity means a future
session sees the forbidden target before it sees a single permitted token, so it
can't accidentally pattern-match to the default. This section also feeds
`compare.html` and the never-regress line in the pre-ship checklist.

### 3. Token map

A pointer to **`css/tokens.css` + `tokens/design-tokens.json` as the source of
truth** (see `references/token-schema.md`), with the **headline tokens inlined**
for quick reference (the accent, background, text, primary font, base spacing,
key radius — enough to recognize the language at a glance without opening the CSS).
The inlined values are a convenience snapshot; the CSS file is authoritative. The
rule is explicit here: build against `var(--token)`, never hardcode.

### 4. Per-dimension rules

One block per dimension (color, typography, spacing, shape, elevation, motion,
imagery, components, patterns, voice). Each block carries:

- **Chosen approach** — the committed direction for that dimension.
- **Intended safeness level (1–5)** — recorded from the `safeness-spectrum`
  choice (`brief.json` → `decisions.<dim>.safeness`). This is load-bearing:
  **future work must match the *intended* adventurousness.** If color was
  deliberately chosen at 4/5 and layout at 2/5, a later session should keep color
  bold and layout conventional — not flatten everything to a safe middle, and not
  make the calm parts loud. The number is how "intentionally adventurous here,
  intentionally conservative there" survives into future sessions.
- **Do / Don't bullets** — concrete, checkable rules for that dimension.

### 5. Component & pattern rules

How the foundations resolve into actual components (buttons, inputs, cards, nav)
and layout patterns (grids, page templates, composition) — the rules that turn
tokens into recognizable UI so two different future sessions build the same
button.

### 6. Pre-ship checklist

The concrete **gate a future session runs before delivering any UI** built in
this language. It is a literal checklist, not prose, so it can be executed:

- [ ] Uses **only palette tokens** — no off-palette / hardcoded colors.
- [ ] Spacing sits **on the scale** (`--space-*`), not arbitrary pixels.
- [ ] **No banned patterns** (the section-2 "never" list).
- [ ] **Matches the intended safeness** per dimension (section 4) — bold where
      bold was chosen, calm where calm was chosen.
- [ ] **NOT the default Claude look** — run the drift checklist in
      `references/anthropic-anti-reference.md`; zero boxes ticked.
- [ ] Accessibility holds (contrast, focus, target sizes, reduced-motion).

This checklist is the operational teeth of the whole contract: identity and rules
describe the language; the checklist is what a session *does* to prove it stayed
inside it.

## Rendered skeleton

A compact example of the assembled contract (values illustrative):

```markdown
# DESIGN_LANGUAGE.md — "Atlas"

> The contract for this design language. Read this BEFORE generating any UI in
> this project. css/tokens.css is the source of truth; this file is the law.

## 1. Identity
**North-star adjectives:** precise · technical · high-contrast · confident

Atlas is a crisp, engineered, high-contrast language for data-dense interfaces.
It favors sharp edges, cool neutrals, and an electric accent — clarity and
density over warmth and calm.

## 2. Anti-reference
This language must NEVER look like:
- The default Claude/Anthropic aesthetic — warm beige/cream backgrounds, a
  clay/terracotta (~#CC785C) accent, literary serif headings, pillowy radii,
  soft warm shadows, cozy-notebook calm. (See anthropic-anti-reference.md.)
- The user's hard constraints: no terracotta; never pure #000 on #fff; no
  all-caps headings; no rounded corners above 6px.

## 3. Token map
Source of truth: `css/tokens.css` and `tokens/design-tokens.json`.
Build against `var(--token)` only — never hardcode values.

| Token | Value |
|-------|-------|
| `--color-bg` | `#0d1117` |
| `--color-accent` | `#3b82f6` |
| `--color-text` | `#e6edf3` |
| `--font-display` | `"Söhne", sans-serif` |
| `--space-unit` | `8px` |
| `--radius-md` | `4px` |

## 4. Per-dimension rules

### Color — intended safeness: 4/5
Chosen: dark cool base, single electric-blue accent, semantic status hues.
- Do: pair `--color-accent` with `--color-accent-contrast` for any CTA.
- Don't: introduce warm/earth tones; don't soften contrast below AA.

### Shape & borders — intended safeness: 2/5
Chosen: tight radii, visible 1px borders for structure.
- Do: use `--radius-sm`/`--radius-md`; separate with `--color-border`.
- Don't: exceed `--radius-md`; don't replace borders with soft shadow.

### Motion — intended safeness: 3/5
Chosen: quick, functional transitions on `--motion-ease`.
- Do: use `--motion-duration-fast` for hovers.
- Don't: add decorative/parallax motion; respect reduced-motion.

<!-- …one block per dimension… -->

## 5. Component & pattern rules
- Buttons: `--radius-sm`, `--space-3`/`--space-4` padding, accent fill on primary.
- Cards: `--color-surface`, 1px `--color-border`, no drop shadow (flat elevation).
- Layout: 12-col grid, gutters on the `--space-*` scale, dense by default.

## 6. Pre-ship checklist
- [ ] Uses only palette tokens (no hardcoded colors)
- [ ] Spacing on the `--space-*` scale
- [ ] No banned patterns (see §2)
- [ ] Matches intended safeness per dimension (see §4)
- [ ] NOT the default Claude look (run anthropic-anti-reference.md drift list)
- [ ] Accessibility: AA contrast, visible focus, ≥44px targets, reduced-motion
```
